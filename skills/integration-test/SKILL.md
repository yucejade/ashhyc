# 集成测试用例制作

> 从设计文档中提取可测试的集成场景，逐步构建完整的集成测试用例集。

## 适用时机

- 设计文档评审完成，需要开始编写集成测试时
- 新模块设计完成，需要补充集成测试范围时
- 需要系统化梳理集成测试覆盖度时

## 阶段一：识别集成测试范围

### 步骤 0：确认集成测试范围

开始提取场景前，**必须先向用户确认集成测试的范围**。

**操作**：

1. **读取架构文档索引**：读取 `docs/index.md`（或项目文档目录中的索引文件），提取 §5 各层详细设计中的模块清单
2. **向用户确认范围**：按层级分组，使用 `AskUserQuestion`（`multiSelect: true`）让用户复选要编写集成测试的模块
   - 每个选项标注：章节号 + 模块名 + 设计文档状态（已确认/待确认）
   - 模块数量超过 4 个时，按层级拆分为多个问题，每组 2-4 个选项
   - 每组提供一个「全部模块」选项方便批量选择
3. **确定测试范围**：仅将用户选定的模块纳入集成测试范围，未选中的模块排除

**分组示例**（根据 index.md 实际内容调整）：

| 问题 | 选项 |
|------|------|
| 基础层 | §5.1.1 核心模块（已确认）、§5.1.2 存储模块（待确认）、§5.1.3 通知模块（待确认）、§5.1.4 日志模块（待确认） |
| 数据层 | §5.3.1 行情接入、§5.3.2 Bar融合、§5.3.3 数据同步、§5.3.4 选股 |
| 业务层 | §5.2 风控层（待确认）、§5.4 策略层（待确认）、§5.5 执行层（待确认） |
| 运行层 | §5.6 运行层（待确认）、§5.7 复盘模块（待确认） |

### 步骤 1：确定范围边界

基于步骤 0 用户确认的范围，明确哪些模块**已设计**（在范围内），哪些**未设计**（排除）。

**操作**：
1. 根据用户选定的范围，列出对应的设计文档文件清单
2. 标记每个文档的状态（已完成设计 / 未设计 / 部分完成）
3. 仅将已完成设计的模块纳入范围

**输出**：`场景与性能风险清单.md` 文件头部声明范围和排除清单。

### 步骤 2：提取场景

逐模块从设计文档中提取**所有**业务场景。

**提取原则**：
- 以设计文档中的**流程图、事件流、职责边界**为主要提取来源
- 每个场景必须对应一个可独立测试的**完整功能单元**
- 覆盖所有类型：正常流程、异常流程、边界条件、恢复流程

**每个场景记录**：
- 场景名称
- 简要描述（输入 → 处理 → 输出）
- 所属模块
- 性能风险等级（见下方定义）

### 步骤 3：过滤不可测试场景

按以下规则**删除**不符合集成测试条件的场景：

#### 规则 1：删除中间件/基础设施机制

不具备独立输入输出的内部机制不应作为独立集成测试场景。

**判断标准**：如果场景的输入和输出**全部是内部事件**（不涉及外部输入或持久化输出），则属于中间件。

**示例**（已删除）：
- EventBus 同步事件分发 — 输入是内部事件，输出也是内部事件分发
- SYSTEM_ERROR 异常处理 — 纯内部异常传播机制

**注意**：如果中间件场景可以通过"喂入事件→检查全局状态/DB"来独立测试，则保留。

#### 规则 2：删除重复场景（保留下层）

当两个场景描述同一流程时，保留**更接近实际业务操作**的场景（上层），删除**底层抽象描述**。

**判断标准**：
- "上层" = 具体的业务模块实现（如行情接入模块的重连机制）
- "底层" = 基础设施层的抽象描述（如核心模块的连接恢复事件定义）

**示例**（保留上层，删除底层）：
- 保留 4.2「断网重连」（行情接入，含恢复订阅细节）→ 删除 1.4「连接恢复」（核心模块，仅定义事件）

**同样规则**：实现细节场景如果已被编排场景包含，删除实现细节、保留编排场景。

**示例**：
- 保留 6.1「盘前同步」（编排层）→ 删除 4.3「历史数据下载」（被盘前同步调用的实现细节）

### 步骤 4：验证输入输出关联

每个保留的场景必须通过以下输入输出验证：

**输入类型**（至少命中一项）：
| 输入 | 含义 | 示例 |
|------|------|------|
| 外部数据 | 来自系统外部的网络数据 | QMT 行情推送、QMT 历史数据 |
| 配置文件 | 系统配置或插件定义 | config.yaml、插件 .py 文件 |
| 持久化数据 | 之前写入的 DB 或文件 | DB 表记录、锁文件 |
| 全局状态 | RuntimeContext 中的已有状态 | positions、universe |

**输出类型**（至少命中一项）：
| 输出 | 含义 | 示例 |
|------|------|------|
| 全局变量 | RuntimeContext 状态更新 | universe、bar_buffer、pending_orders |
| DB 写入 | 数据持久化 | 行情记录、订单记录、universe 表 |
| 文件 | 文件系统操作 | 锁文件创建/删除、报告文件生成 |
| 事件发布 | 触发下游处理的可观测事件 | UNIVERSE_READY、MARKET_BAR |

**验证方法**：逐场景检查，确认每个场景都能写出一个独立的集成测试用例（给定输入 → 验证输出）。场景之间允许有交叉功能，但每个场景的**总体功能必须独立**。

### 步骤 5：评估性能风险

对每个场景评定性能风险等级：

| 等级 | 星级 | 判断标准 |
|------|------|---------|
| 高 | ★★★★★ | 涉及高频操作、大数据量、严格延迟要求、关键路径阻塞风险 |
| 中 | ★★★☆☆ | 涉及批量操作、启动/恢复路径、有超时风险但非实时路径 |
| 低 | ★☆☆☆☆ | 非实时路径、操作频率低、数据量小 |
| 无 | ☆☆☆☆☆ | 纯逻辑判断、一次性操作、不涉及数据处理 |

### 步骤 6：汇总与矩阵

1. 按风险等级汇总场景清单（高/中/低/无）
2. 生成「模块 × 风险等级」矩阵，统计各模块的场景数量
3. 对高风险场景标注**核心风险**和**集成测试关注点**

## 阶段一输出格式

```
docs/集成测试/
└── 场景与性能风险清单.md    # 范围识别结果
```

文件结构：
1. 范围声明（含/不含）
2. 风险等级定义
3. 逐模块场景详述（名称、描述、风险、测试关注点）
4. 风险汇总表
5. 模块 × 风险矩阵

## 阶段二：编写集成测试用例

> 基于阶段一识别的场景清单，生成完整的集成测试用例集。

### 前置条件

- 阶段一的 `场景与性能风险清单.md` 已完成
- 相关模块的详细设计文档已读取完毕

### 步骤 1：读取设计文档

**分批读取**：按模块分批并行读取，每批不超过 4 个文档，避免上下文溢出。

对每批文档提取以下信息：
- 流程图和事件流（每个步骤的具体操作）
- 边界条件（时间边界、数量边界、状态边界）
- 异常处理流程（错误类型、恢复策略）
- 配置项（config.yaml 中影响该场景的字段及取值范围）
- DB 表操作（读/写哪些表、字段含义）

### 步骤 2：确认输入输出约束

使用 `AskUserQuestion` 向用户展示以下常用选项，让用户**复选**本项目允许的输入来源和输出验证方式。用户选定的结果即为后续步骤的**约束边界**。

**输入来源选项**：

| 选项 | 说明 | 典型场景 |
|------|------|---------|
| 配置文件 | YAML/JSON/TOML 等配置文件 | 修改 config.yaml、放置插件 .py 文件 |
| 网络外部系统 | 外部 API、数据推送、远程服务 | 交易所行情推送、REST API 调用、WebSocket 数据 |
| 用户输入 | 键盘、鼠标、命令行交互 | 按下 Ctrl+C、命令行参数、界面点击 |
| 磁盘文件 | 文件系统上的文件操作 | 删除/创建 DB 文件、放置/修改插件文件、读写锁文件 |
| 数据库 | 直接操作数据库写入测试数据 | 往表中插入预设记录 |
| 环境变量 | 系统环境变量 | 设置 API_KEY、DEBUG 模式 |
| 系统时钟 | 修改系统时间或模拟时间 | 模拟跨日、模拟交易时段切换 |

**输出验证选项**：

| 选项 | 说明 | 典型场景 |
|------|------|---------|
| DB 内容 | 查询数据库表验证数据 | 检查 orders 表记录、验证字段值 |
| 磁盘文件 | 检查文件存在性和内容 | 检查锁文件已删除、报告文件内容正确 |
| 画面显示 | 终端/日志/UI 上的文字输出 | 日志输出"启动完成"、控制台错误信息 |
| 网络请求 | 检查系统发出的外部请求 | 验证向交易所发送的下单请求内容 |
| 系统进程 | 检查进程状态 | 进程已退出、子进程已启动 |
| 性能指标 | 耗时、内存、CPU 等量化指标 | 响应时间 < 100ms、内存增长 < 50MB |

**操作方式**：
1. 使用 `AskUserQuestion`，`multiSelect: true`，分别让用户勾选输入来源和输出验证
2. 用户选定后，将选项记录到输出文件的「约定」章节
3. 步骤 6 编写测试用例时，**只能使用用户选定的输入和输出类型**
4. 如果用户跳过不选，则使用全部选项作为默认

### 步骤 3：输入数据分类分析

回到详细设计文档，对场景清单中每个场景的**输入数据**按优先级进行分类。

#### 剪枝规则（防止上下文溢出）

在执行分类前，先对输入数据项进行优先级划分，**仅对高优先级字段做全量分析**：

| 优先级 | 判断标准 | 分析要求 |
|--------|---------|---------|
| **必填字段** | 设计文档标注"必填"或"无默认值" | 全量分析（属性+状态+数值） |
| **条件必填字段** | 特定模式下必填（如回测需 start_date） | 全量分析 |
| **高风险可选字段** | ★★★以上场景涉及的参数 | 全量分析 |
| **普通可选字段** | 有安全默认值、非关键路径 | **仅分析"字段缺失"一个状态变体，跳过属性和数值变体** |

**分类维度**：

| 维度 | 说明 | 示例 |
|------|------|------|
| 属性 | 输入数据的外部特征 | 文件不存在、网络不可达、目录权限不足 |
| 状态 | 输入数据的内容状态 | 内容为空、格式错误、必填项缺失、非必填项缺失、数据过期 |
| 数值 | 输入数据的具体取值 | 重试次数 0/1/-1、股票数量 0/1/50/51、金额 0/负数/超大值 |

**操作方法**：
1. 对每个场景，列出步骤 2 确认的全部输入数据项
2. 按剪枝规则划分优先级，普通可选字段标注"仅测缺失"
3. 对高优先级字段，按属性、状态、数值三个维度逐一分析变体
4. 对数值维度的变体，**过滤等价类**——将产生相同系统行为的值归为一组，每组只保留一个代表值

**分批输出**：当配置字段超过 15 个时，按模块分批输出分类表，每批不超过 10 个字段。

**输出格式**：

```markdown
#### {场景名称} 输入数据分类

| 输入项 | 优先级 | 属性变体 | 状态变体 | 数值变体（已过滤等价类） |
|--------|--------|---------|---------|----------------------|
| system.mode | 必填 | — | 内容为空 | live/paper/backtest/review |
| data.qmt_path | 条件必填 | 路径不存在 | 内容为空 | 有效路径 |
| data.reconnect_interval | 普通可选 | — | 字段缺失 | —（仅测缺失） |
```

### 步骤 4：输入组合与输出预测

基于步骤 3 的分类结果，对**高优先级字段**进行成对组合，生成测试输入矩阵并预测输出。

#### 组合适用范围（防止组合爆炸）

**参与组合的字段**（必须同时满足）：
- 步骤 3 标记为"必填"、"条件必填"或"高风险可选"的字段
- 字段之间存在**交互关系**（一个字段的取值影响另一个字段的行为）

**不参与组合的字段**：
- 普通可选字段（有安全默认值）→ 单独测试"字段缺失"即可
- 独立字段（取值不影响其他字段）→ 单独测试各变体即可

**组合数量限制**：每个场景的组合数不超过 **10 组**。

**操作方法**：
1. 从步骤 3 的分类表中筛选高优先级且互相关联的字段
2. 仅对这些字段按成对组合（Pairwise）展开
3. 对照详细设计文档，为每组输入**预测**系统的预期输出

**组合策略**：

| 输入项数 | 推荐策略 | 说明 |
|---------|---------|------|
| 1-2 项 | 全排列 | 组合数少，全部覆盖 |
| 3-5 项 | 成对组合（Pairwise） | 保证任意两项的所有变体组合至少出现一次 |
| 6+ 项 | 正交表 + 风险优先 | 先用正交表缩减，再补充高风险组合 |

**输出格式**：

```markdown
#### {场景名称} 输入组合矩阵

| 组合编号 | 输入项A | 输入项B | 输入项C | 预期输出（依据设计文档§章节） |
|---------|---------|---------|---------|------------------------|
| C1 | 正常值 | 正常值 | 正常值 | 正常流程（§5.3.2 步骤3） |
| C2 | 文件不存在 | 正常值 | 正常值 | 启动失败+错误日志（§5.3.2 异常处理） |
| C3 | 正常值 | 内容为空 | 正常值 | 降级处理+默认值（§5.3.3 降级策略） |
```

**注意**：
- 预期输出必须引用设计文档的具体章节编号，确保可追溯
- 无法从设计文档确定的输出标记为「待确认」，由用户补充
- 步骤 6 编写正式用例时，直接从本步骤的组合矩阵中选取

### 步骤 5：确定用例类型覆盖

对每个场景，按以下规则决定需要生成哪些类型的测试用例：

| 类型 | 标记 | 说明 | 必要性 |
|------|------|------|--------|
| 正常功能 | N | 正常输入下的预期行为 | 每个场景必有 |
| 异常功能 | A | 异常输入或外部故障时的行为 | 有异常路径时必有 |
| 性能 | P | 耗时、吞吐量、内存等指标 | ★★★ 以上场景必有 |
| 边界 | B | 临界值、零值、最大值、状态切换 | 有明确边界时必有 |

### 步骤 6：编写单个测试用例

每个测试用例严格遵循以下格式：

```markdown
#### TC-{模块号}-{场景号}-{类型序号} {用例标题}

**用例描述**：用白话描述测试目的，让人一看就懂。

**测试方法**：
1. 准备输入数据（注明来源类型）
2. 执行操作步骤
3. ...

**预想结果**：
- {输出类型}：具体验证内容
- {输出类型}：具体验证内容
- ...

**结果**：☐ 通过 / ☐ 不通过 / ☐ 未测试
```

**编写纪律**：
- **用例描述**：纯白话，不涉及代码内部术语（函数名、变量名等）
- **测试方法**：每个步骤的输入必须标注来源类型（括号注明），只使用步骤 2 用户选定的输入来源
- **预想结果**：每个验证点必须标注输出类型，只使用步骤 2 用户选定的输出验证方式
- **结果**：统一使用复选框格式

### 步骤 7：精简与合并用例

初版用例写完后，按以下规则检查并精简：

#### 规则 1：删除被完全覆盖的用例

如果用例 A 的测试方法是用例 B 的子集，且预想结果也是 B 的子集，则**删除 A**，将 A 的独特验证点合并到 B 的预想结果中。

**判断方法**：逐对比较测试方法文本，如果 A 的步骤完全包含在 B 中，检查 A 的预想结果是否已在 B 中体现。

**示例**：
- "完整配置加载"的测试方法 = "正常启动"的测试方法 → 删除前者，将"配置加载成功"的验证点加入后者的预想结果
- "插件初始化 on_init 成功"的测试方法 = "插件加载成功"的测试方法 → 删除前者

#### 规则 2：合并同测试方法的多用例

如果多个用例的**测试方法相同**（或可以通过一次执行覆盖），且预想结果不冲突，则**合并为一个用例**，预想结果取并集。

**合并条件**（必须同时满足）：
1. 测试方法的输入和操作步骤相同
2. 合并后每个预想结果仍可独立验证
3. 不需要额外的前置条件

**操作方式**：
1. 按模块逐组检查，找出测试方法相同的用例
2. 合并后保留第一个用例的编号，标题改为涵盖所有功能
3. 预想结果**全部保留**，不删减

**常见合并模式**：

| 模式 | 说明 | 示例 |
|------|------|------|
| 首次启动 | 系统首次启动同时验证建表、插件注册、全量同步 | 启动初始化 + 建表 + 插件注册 + 全量数据同步 |
| 重复启动 | 正常停止后重启同时验证幂等性和跳过注册 | 数据不丢失 + 插件表不变 |
| 崩溃恢复 | 杀进程后重启同时验证锁清理、Bar 恢复、跳过选股 | 锁清理 + Bar 连续 + 订单恢复 + 选股跳过 |
| 盘后流程 | 收盘后同时验证盘后同步和日 K 完成 | 盘后数据写入 + 日 K 发布事件 |
| 性能合并 | 同一操作的不同性能指标 | 写入延迟 + 对读取影响 |

#### 规则 3：更新统计

合并后更新文档末尾的统计附录，反映精简后的实际用例数。

### 步骤 8：补充边界用例

对每个场景检查是否存在以下边界，如有则补充用例（注意：合并后仍需检查边界是否已被合并用例覆盖）：

| 边界类型 | 检查项 |
|---------|--------|
| 零值边界 | 空列表、空字符串、0 条记录、无数据 |
| 上限边界 | 最大数量（如 50 只股票、10 次重试） |
| 时间边界 | 精确到秒的时间切换点（如 09:00、15:30） |
| 状态切换 | 从状态 A 切换到状态 B 的瞬间 |
| 首次/重复 | 首次执行 vs 重复执行（幂等性） |
| 数据缺失 | 必需数据不存在时的降级 |

### 步骤 9：汇总与输出

在文档末尾添加统计附录：

1. **模块统计表**：按模块统计 N/A/P/B 四类用例数量
2. **高风险场景覆盖表**：对阶段一的 ★★★★★ 场景，列出对应的用例数量，确保每个高风险场景至少 3 个用例
