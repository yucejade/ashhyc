# 文档 Skill

> 编写或修改设计文档、进行设计讨论时加载此文件。

## 文档修改原则

- **审查/重构结果优先**：刚审查/重构过的内容应视为权威来源，其他文档如果与之不一致，应修改其他部分向其对齐，而不是把刚审查/重构过的内容按旧逻辑改回去。不确定方向时先问用户。
- **时间顺序参考**：多份文档描述同一内容时，后编写/修改的文档通常更准确。提修改建议/回答用户问题时优先以后改的文档为准。
- **逻辑自洽验证**：提修改建议/回答用户问题要与优先参考文档（时间顺序参考）保持逻辑一致，不能有冲突或矛盾的地方。
- **修改内容要有根据**：任何修改都应有明确的理由和依据，不得随意更改。

## 写作规范

### 术语与用词

- **同一概念统一用词**：同一操作或概念在文档中必须使用完全相同的表述，不得用不同词语描述同一件事。如需缩写，在首次定义时声明。

  **反例**：前文称"历史数据补充源"，后文突然称"补充源"且未声明缩写；前文称"选股池"，后文称"股票池"，再后文称"universe" — 指同一事物。

  **正例**：首次使用："选股池（universe）"，后续统一用"选股池"。

- **术语首次出现时必须定义**：文档中引入的专有术语、缩写、概念在首次使用时必须给出明确说明。不依赖读者"应该知道"。

  **反例**："接口层使用 SSE/SZSE" — "接口层"指哪一层？数据源接口？系统对外接口？

  **正例**："DataSourceBase 方法参数使用 SSE/SZSE，QmtDataSource 内部转换为 QMT 的 SH/SZ"

- **新概念引入规范**：文档中引入新概念时，必须先明确定义、性质、优缺点，并论证其与当前使用场景的匹配性后才能引入。不得无铺垫地使用未定义的概念。

### 抽象层级

- **流程描述用领域语言，不用代码变量**：流程描述应使用读者理解的领域术语，不混入实现层的变量名、方法名、条件表达式。

  **反例**："将 `_primary` 的结果缓存到 `_history` 中"、"检查 `if period in ("1d", "1w", "1mo")` 则写入日级表"

  **正例**："将主数据源的查询结果缓存到历史补充源"、"日级及以上周期写入日级表"

- **接口设计只写签名，不写实现**：接口设计节描述"做什么"（签名 + 参数说明），不写"怎么做"（条件分支、异常处理、内部数据结构操作）。方法体用 `...` 省略。

### 描述精确性

- **模糊描述补充判定条件**：文档中出现"适当"、"合理"、"必要时"等模糊词时，必须给出具体判定条件或量化标准。

  **反例**："Tick 数量不足时回退" — 多少算"不足"？"超时后执行降级" — 超时多少？

  **正例**："Tick 数量 < 全天预期数量的 50% 时回退"、"选股超时 > 120 秒后执行降级"

- **场景覆盖不能遗漏分支**：设计文档描述流程时，必须覆盖所有分支路径（正常路径、异常路径、边界路径），不能只写 happy path。

  **检查方法**：每个流程问"如果这一步失败会怎样？如果输入为空会怎样？如果部分成功会怎样？"

### 第三方依赖

- **第三方接口核实**：引用第三方库或外部数据源时，必须先到官方文档确认数据结构、接口参数等内容，再基于核实后的信息回答。不得凭记忆假设接口细节。
- **第三方依赖逻辑一致**：当前定义功能或逻辑与第三方库接近时，需考虑是否能与三方库接口或流程上一致。
- **字段注释格式**：涉及第三方数据源的字段统一使用标准注释格式，包含来源标注和适配说明（如有格式转换）。

### 其他

- **流程校验优先**：回答问题前，先将问题和关联模块放入整体流程中按时间线校验，确认逻辑合理后再做回答。不得脱离上下文孤立作答。
- **不可引入讨论以外的内容**：在文档生成前检查是否所有内容都与用户进行过讨论，如果有需要立刻与用户进行讨论，而不是生成到新文档中。
- **再次确认问题**：输出回复内容前，再次检查回复内容是否解答了用户的问题。

## 跨文档一致性

- **跨文档的契约定义保持一致**：一个模块与其他模块的契约关系（接口依赖、数据格式约定、消息订阅/发布等），在总览文档和子模块文档中必须一致。发现矛盾时以总览文档为准，子文档对齐。

  **检查方法**：总览文档列出的模块契约关系与每个子文档的描述交叉比对。

  **反例**：总览文档称模块 A"依赖"服务 X，子文档称模块 A"不依赖"服务 X。

  **正例**：两者描述一致，且角色描述一致。

- **设计变更同步更新所有受影响文档**：一个设计决策变更后，必须找到所有引用该决策的文档并同步更新，不留孤立的不一致。

  **检查方法**：修改一处后，全文搜索相关关键词，逐个确认。

- **编号、计数与实际内容同步**：文档中的编号（章节号、条目数、总数声明）必须与实际内容一致。增删条目后立即修正编号和计数声明。

## 文档与实现一致性

- **文档描述的行为必须与代码实现一致**：当设计文档与代码实现出现差异时，以设计文档为基准。差异需上报用户确认是文档问题还是代码问题。
- **设计定义与所有实现形式保持一致**：字段名称、类型、约束在所有实现形式中必须一致 — 设计文档描述、代码类型定义、数据库/存储结构定义。任何一处变更必须同步更新其余位置。

## 验证与测试

- **验证程序按端到端流程组织，不按组件组织**：验证程序应描述完整的业务流程（从起点事件到终点验证），而非单个组件的功能验证。每条验证覆盖多个组件的协作。

  **反例（按组件）**："BarBuilder 正确更新 OHLCV"、"BarManager Tick 分发到各 BarBuilder"

  **正例（按流程）**："UNIVERSE_READY → 创建 BarBuilder → Tick 聚合 → Bar 完成 → 写入 DB"

## 评审纪律

- **未经核实不得发表判断**：回答设计合理性问题时，必须先查阅决策记录、讨论记录、设计文档等材料，比对后再判断。禁止凭印象说"没问题"或"不合理"。
- **查到材料必须汇报核心内容**：查阅到决策记录或讨论记录后，不能只说"有记录"或"已确认"，必须汇报：**来源**（文件路径 + 位置）、**核心内容**（决策的关键原则或结论）、**判断**（基于材料得出的判断）。

## 结构规范

- **设计变更记录原因和影响范围**：每次设计变更在文档中应记录：为什么改（原因）、改了什么（范围）、影响了哪些其他文档/模块（影响面）。
- **接口变更列出完整受影响方**：接口签名变更时，列出所有调用方和受影响的下游模块，不遗漏。

## 按需加载参考

编写文档时，按需加载项目中的模块参考文件和技术参考。

## 写文档前检查

- [ ] 相关模块的架构文档已读取
- [ ] 关联的设计决策已查阅（`.claude/QA/decision/`）
- [ ] 用词与已有文档一致（遵循统一用词规范）
- [ ] 引用的第三方接口已核实
- [ ] 新概念已定义和论证
- [ ] 所有内容已与用户讨论过
- [ ] 跨文档的契约关系已交叉比对
- [ ] 编号/计数与实际内容一致
