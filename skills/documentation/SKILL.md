# 文档 Skill

> 编写或修改设计文档、进行设计讨论时加载此文件。

## 文档修改原则

- **审查/重构结果优先**：刚审查/重构过的内容应视为权威来源，其他文档如果与之不一致，应修改其他部分向其对齐，而不是把刚审查/重构过的内容按旧逻辑改回去。不确定方向时先问用户。
- **时间顺序参考**：多份文档描述同一内容时，后编写/修改的文档通常更准确。提修改建议/回答用户问题时优先以后改的文档为准。
- **逻辑自洽验证**：提修改建议/回答用户问题要与优先参考文档（时间顺序参考）保持逻辑一致，不能有冲突或矛盾的地方。
- **修改内容要有根据**：任何修改都应有明确的理由和依据，不得随意更改。

## 写作规范

- **同一概念统一用词**：同一操作或概念在文档中必须使用完全相同的表述，不得用不同词语描述同一件事。INSERT 操作统一用"写入 {表名}"，UPDATE 操作统一用"更新 {表名}"，涉及多表用"+"连接。
- **字段注释格式**：涉及第三方数据源的字段统一使用标准注释格式，包含来源标注和适配说明（如有格式转换）。
- **流程校验优先**：回答问题前，先将问题和关联模块放入整体流程中按时间线校验，确认逻辑合理后再做回答。不得脱离上下文孤立作答。
- **第三方接口核实**：引用第三方库或外部数据源时，必须先到官方文档确认数据结构、接口参数等内容，再基于核实后的信息回答。不得凭记忆假设接口细节。
- **第三方依赖逻辑一致**：当前定义功能或逻辑与第三方库接近时，需考虑是否能与三方库接口或流程上一致。
- **新概念引入规范**：文档中引入新概念时，必须先明确定义、性质、优缺点，并论证其与当前使用场景的匹配性后才能引入。不得无铺垫地使用未定义的概念。
- **不可引入讨论以外的内容**：在文档生成前检查是否所有内容都与用户进行过讨论，如果有需要立刻与用户进行讨论，而不是生成到新文档中。
- **再次确认问题**：输出回复内容前，再次检查回复内容是否解答了用户的问题。

## 按需加载参考

编写文档时，按需加载项目中的模块参考文件和技术参考。

## 写文档前检查

- [ ] 相关模块的架构文档已读取
- [ ] 关联的设计决策已查阅（`.claude/QA/decision/`）
- [ ] 用词与已有文档一致（遵循统一用词规范）
- [ ] 引用的第三方接口已核实
- [ ] 新概念已定义和论证
- [ ] 所有内容已与用户讨论过
